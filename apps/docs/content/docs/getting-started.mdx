## Install

wfc needs Node.js 22 or newer. The npm package is `workflow-contracts`; the command is `wfc`.

<Tabs items={["Global", "Project (npm)", "Project (pnpm)", "One-off", "mise"]}>
<Tab value="Global">
Install once and use `wfc` anywhere:

```sh
npm install --global workflow-contracts
wfc lint
```
</Tab>
<Tab value="Project (npm)">
Pin the version for everyone working on the repository (and its CI):

```sh
npm install --save-dev workflow-contracts
npx --no wfc lint
```

`--no` makes npx use the installed `wfc` and never download anything (see the note below).
</Tab>
<Tab value="Project (pnpm)">
```sh
pnpm add -D workflow-contracts
pnpm wfc lint
```
</Tab>
<Tab value="One-off">
```sh
npx workflow-contracts@0 lint
```
</Tab>
<Tab value="mise">
```sh
mise use --global npm:workflow-contracts
wfc lint
```
</Tab>
</Tabs>

<Callout type="warn" title="Use the package name with npx">
The npm package is `workflow-contracts`. A different, unrelated package is called `wfc`, so `npx wfc` in a directory
without wfc installed would download and run that package instead. Use `npx workflow-contracts …`, or
`npx --no wfc …` where wfc is installed.
</Callout>

In GitHub Actions, use the [action](/docs/action) instead: it needs neither Node.js nor an install.

## First run

<Steps>
<Step>
### Lint the repository

```sh
wfc lint
```

wfc reads `.github/workflows/*.yml` and every local action (`action.yml` under `.github/actions/`, plus any other
directory a `uses: ./path` points to). It always loads the whole repository, because most problems span files.
</Step>
<Step>
### Read a finding

Each finding shows, top to bottom:

| Part | Meaning |
| --- | --- |
| `✖ ERROR WFC401 empty-binding-for-matrix-combo` | severity, stable code and rule name |
| message | what is wrong, in one sentence |
| `▶ file:line:col` + code frame | exactly where, with the expression underlined |
| `matrix` | the affected matrix combinations (matrix rules only) |
| `context` | related locations — the call chain from the top-level workflow, the include entry, the receiving input |
| `why` / `fix` | why it matters and what to change |
| `docs` | a link to the rule page (clickable in terminals that support hyperlinks) |

The run ends with a summary card: counts per severity, files, jobs, matrix combinations, graph size and the most
frequent codes.
</Step>
<Step>
### Dig deeper

```sh
wfc explain WFC401                      # why/fix/examples for a code
wfc trace pipeline.yml:config           # where does this input go?
wfc trace run-suite.yml:config --up     # where does this value come from?
```
</Step>
<Step>
### Narrow it down

```sh
wfc lint .github/workflows/release.yml  # only report on some files (everything is still analyzed)
wfc lint --only WFC401,WFC101           # only run some rules
wfc lint --hide-info                    # list errors and warnings only
```
</Step>
</Steps>

## Next steps

<Steps>
<Step>
### Lock the interfaces

```sh
wfc generate        # write .github/workflow-contracts/**/*.contract.yml
git add .github/workflow-contracts && git commit -m "Add workflow contracts"
wfc check           # lint + compare with the committed contracts
```

[Contracts](/docs/contracts) make every change to an input, secret, output or call visible in review, and `wfc check`
fails on breaking changes.
</Step>
<Step>
### Run it in CI

Add the [GitHub Action](/docs/action) or the CLI to a workflow — see [CI usage](/docs/ci).
</Step>
<Step>
### Tune it

Change severities, accept specific findings with a reason and an expiry date, or add your own rules in the
[configuration](/docs/configuration).
</Step>
</Steps>

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | No findings at or above `--fail-on` (default: `error`) |
| `1` | Findings at or above `--fail-on` (in `wfc check`, this includes contract drift) |
| `2` | Usage or configuration error (unknown rule, invalid config, plugin that fails to load, nothing to analyze) |
| `3` | Internal error — please [report it](https://github.com/rumankazi/wfc/issues) with `--debug` output |
