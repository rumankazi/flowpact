title: Build on flowpact
description: Run flowpact inside your own action, CI template or tool — the interfaces that stay stable, a reference wrapper action, organization defaults and rules, and keeping the version current.
---

Organizations that cannot use a third-party action, or that want their own defaults, rules and reports, can wrap
flowpact instead of forking it: an internal action or CI template that runs the CLI from npm. The wrapper owns the
policy (rules, when to fail, where reports go); flowpact stays an unmodified dependency that you verify and update with
a version bump.

## What is stable

Build on these. A release that changes one in an incompatible way says so under **Breaking changes** in its release
notes, with [upgrade notes](/docs/upgrading). Before 1.0, that can happen in a minor release (0.8 → 0.9), never in a
patch release.

| Interface | Reference |
| --- | --- |
| CLI commands, flags and exit codes | [CLI](/docs/cli) |
| JSON report | [`/schemas/report/v1.json`](/schemas/report/v1.json); an incompatible change makes it v2, and `meta.schemas.report` says which a report follows |
| SARIF | SARIF 2.1.0, with stable fingerprints in `partialFingerprints["flowpact/v1"]` |
| Annotations | `--format github`: GitHub workflow commands |
| Config and contracts | [`/schemas/config/v1.json`](/schemas/config/v1.json), [`/schemas/contract/v1.json`](/schemas/contract/v1.json) |
| Rule codes and names | [Rules](/docs/rules); configs, overrides and `--only` refer to them |
| Plugin rules | The rule object in [Custom rules](/docs/custom-rules) |
| GitHub Action inputs and outputs | [GitHub Action](/docs/action) |

Not stable: the terminal output and the wording of messages and Markdown reports, which are written for people (parse
JSON or SARIF instead), and the `@flowpact/*` packages inside the repository, which are not published. flowpact has no
library API; the CLI is the interface.

## A wrapper action

An internal repository with a composite action that installs a pinned flowpact and runs it with your defaults:

```text
acme/flowpact-action
├── action.yml
├── package.json        # flowpact, pinned to an exact version
├── package-lock.json   # and its integrity hash
├── acme.base.yml       # optional: organization defaults (below)
└── rules/acme.mjs      # optional: organization rules (below)
```

Create `package.json` and the lockfile with `npm install --save-exact flowpact@0.9`. The flowpact package has no
dependencies of its own: it is one bundled file, with its license notices and an SBOM next to it.

```yaml title="action.yml"
name: Acme flowpact
description: flowpact with Acme's rules and reports
inputs:
  command:
    description: lint, or check when the repository commits contracts
    default: lint
runs:
  using: composite
  steps:
    - uses: actions/setup-node@v7 # pin to a commit SHA
      with:
        node-version: 22
    - name: Install flowpact
      shell: bash
      run: npm ci --prefix "$GITHUB_ACTION_PATH" --ignore-scripts
    - name: Run flowpact
      shell: bash
      env:
        COMMAND: ${{ inputs.command }}
        # The repository's own plugins run its code: not on events that run a fork's code with secrets.
        NO_PLUGINS: ${{ contains(fromJSON('["pull_request_target", "workflow_run"]'), github.event_name) && '--no-plugins' || '' }}
      run: >-
        "$GITHUB_ACTION_PATH/node_modules/.bin/flowpact" "$COMMAND"
        --format github
        --base-config "$GITHUB_ACTION_PATH/acme.base.yml"
        --plugin "$GITHUB_ACTION_PATH/rules/acme.mjs"
        $NO_PLUGINS
        -o markdown:"$GITHUB_STEP_SUMMARY"
        -o flowpact.sarif
```

From one run, this gives:

- the organization's defaults and rules, under each repository's own config;
- an annotation on the file and line of each finding, in the run and the pull request (`--format github`);
- the Markdown report in the job summary (`-o markdown:"$GITHUB_STEP_SUMMARY"`);
- `flowpact.sarif`, for `github/codeql-action/upload-sarif` in the calling job or in the wrapper;
- a failed step when there are errors (exit code `1`); add `--fail-on warning` or `--fail-on never` to change that.

Repositories use it like any action, after `actions/checkout`. With `--root` (a repository in a subdirectory of the
workspace), the paths in annotations, SARIF and Markdown links stay relative to the repository.

Without access to the npm registry, install the npm package from a release instead: each
[GitHub release](https://github.com/rumankazi/flowpact/releases) has `flowpact-X.Y.Z.tgz` with build provenance.
[Verify it](/docs/security#verify-a-release), commit it to the wrapper and depend on the file
(`npm install --save-exact ./flowpact-X.Y.Z.tgz`). To run the flowpact action itself from an internal repository,
mirror its release archive, `flowpact-action-X.Y.Z.tar.gz`, the same way.

## Organization defaults

A [base config](/docs/configuration#base-config) holds settings for every repository, and each repository's own config
goes on top of it. The wrapper passes it with `--base-config`:

```yaml title="acme.base.yml"
rules:
  FP105: error                     # stricter than flowpact's default
  needs-without-data: info         # an opt-in rule, on for everyone
  prod-deploy-needs-approval: error
ignore:
  - .github/workflows/generated/
impact:
  declaredBy: labels               # Acme declares release impact with labels
```

- `rules`, `limits` and `impact` settings merge key by key, and the repository's value wins: a repository can still set
  `FP105: warning`. `ignore` and `generated` lists add up.
- Settings that name files of one repository (`overrides`, `matrixShapes`, `repository`, `impact.publish`) and
  `plugins` are config errors in a base config.
- In [impact mode](/docs/impact-mode), the base config also applies under the baseline's config.

Repositories keep a config that works on its own: locally and in the editor, without the wrapper, flowpact uses the
repository's config and its defaults.

## Organization rules

Write your rules as [plugins](/docs/custom-rules) and ship them in the wrapper, such as `rules/acme.mjs` with the
`prod-deploy-needs-approval` rule from [Custom rules](/docs/custom-rules):

- `--plugin <file>` loads a plugin in addition to those the repository's config lists. It is relative to the working
  directory, and can be repeated.
- `--no-plugins` skips the repository's plugins, which run the repository's code, but not the ones given with
  `--plugin`. The wrapper's rules keep running on untrusted events.
- The base config sets how strict each rule is, and a repository can change that under `rules:` or accept a finding
  with an [override](/docs/configuration#overrides), like for built-in rules. Where the rule is not loaded (plain
  `flowpact lint`, the editor), those entries are [ignored with a warning](/docs/configuration#rules-that-are-not-loaded).

```yaml title=".github/flowpact/flowpact.config.yml (in one repository)"
rules:
  FP105: warning                   # this repository wins over the base config
overrides:
  - rule: prod-deploy-needs-approval
    target: .github/workflows/deploy.yml#jobs.hotfix
    reason: Hotfix deploys are approved in the incident channel (INC-142)
    expires: 2026-12-31
    owner: '@acme/sre'
```

## Reading the results

For a wrapper that decides by itself, run with `--fail-on never` and read the JSON report:

```sh
flowpact lint --fail-on never --format json > flowpact.json
jq -r '.findings[] | "\(.severity) \(.code) \(.loc.file):\(.loc.line)"' flowpact.json
jq '.summary.errors' flowpact.json
```

- Exit codes: `0` no findings at or above `--fail-on`, `1` findings, `2` usage or config error, `3` internal error.
- `fingerprint` stays the same across unrelated edits, so a finding can be tracked over time or compared with a
  baseline.
- `symbol` names what the finding is about; it is the `target` of an override.
- Logs go to stderr and never mix with the report on stdout.

## Keeping it current

Renovate updates the wrapper's npm dependency, and pinned action references wherever flowpact's own action is used:

```json title="renovate.json"
{
  "extends": ["config:recommended", "helpers:pinGitHubActionDigests"],
  "packageRules": [
    {
      "matchPackageNames": ["flowpact", "rumankazi/flowpact"],
      "groupName": "flowpact",
      "minimumReleaseAge": "3 days"
    }
  ]
}
```

- `minimumReleaseAge` waits a few days after a release before proposing it.
- Before 1.0, read the **Breaking changes** section of a minor update before merging it; patch updates can be merged
  automatically (`"matchUpdateTypes": ["patch"], "automerge": true`).
- `npm audit signatures` in the wrapper's CI checks that the installed version was published from this repository's
  release workflow.
- Dependabot works the same way, with the `npm` and `github-actions` ecosystems.

## Why not extends

Tools such as ESLint let a config extend another file. flowpact's base config comes from the command line instead,
for two reasons:

- A repository's config that extends a file in the wrapper, or in a private package, points at something that is not
  there when a developer runs `flowpact lint` or opens the editor, so the config would fail everywhere but in CI. Passed
  by the wrapper, the base config applies where the wrapper runs, and the repository's config still works alone.
- The organization applies its defaults: a repository cannot leave them out by deleting a line.

## Why not a fork

A fork that changes flowpact's code has to be rebuilt, re-verified and merged on every release, and its bundle no
longer matches the signed release. A wrapper keeps flowpact unmodified and adds what your organization needs around it.
If it needs something flowpact does not offer — a flag, an output, an extension point —
[open an issue](https://github.com/rumankazi/flowpact/issues).
